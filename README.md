# seWer Tauri — сборка на Tauri v2

Та же версия 1.0.0, что в electron-репозитории, но оболочка переписана:
electron (101 МБ инсталлятор, 223 МБ развёрнуто, отдельный chromium) →
tauri + webview2 системы. Логика плеера и весь интерфейс перенесены без
изменений.

## это отдельная сборка, не замена electron-версии

Обе версии можно держать установленными рядом, и они не мешают друг другу.
Всё, что могло бы конфликтовать, разведено суффиксом `-tauri`:

| что | electron | tauri |
|---|---|---|
| productName | `seWer` | `seWer Tauri` |
| identifier | `com.sewer.app` | `com.sewer.tauri` |
| cargo/npm | `sewer` | `sewer-tauri` |
| папка данных | `%APPDATA%\sewer` | `%APPDATA%\sewer-tauri` |
| инсталлятор | `sewer Setup 1.0.0.exe` | `seWer Tauri_1.0.0_x64-setup.exe` |
| ключ автозагрузки | `seWer` | `seWer Tauri` |

Важен пункт с папкой данных: общая `%APPDATA%\sewer` означала бы общий
`settings.json` — автозапуск, включённый в одной сборке, и папка с музыкой
из другой перетирали бы друг друга при каждом запуске.

## логин soundcloud: почему он такой

Сначала здесь был вариант «implicit oauth + deep-link»: открыть
`/connect?client_id=…&redirect_uri=sewer-tauri://callback` в системном
браузере и поймать токен из редиректа. **Он не работает, и это не
настройка.** Connect-эндпоинт soundcloud отвечает `410 Gone` на любой
`redirect_uri`, не зарегистрированный за их приложением — проверено на
`sewer-tauri://`, `urn:ietf:wg:oauth:2.0:oob` и `http://localhost`, везде
410. Свой `client_id` без регистрации приложения на soundcloud.com/developers
не получить, так что этот путь закрыт наглухо.

Рабочий путь — тот же, что был в electron, только перехват переехал внутрь
страницы. Открывается окно входа soundcloud, в его контексте **до** загрузки
сайта ставятся обёртки на `XMLHttpRequest.setRequestHeader` и `fetch`, и из
запросов, которые сайт шлёт сам себе, снимается `Authorization: OAuth …`.
Сайт при этом работает как обычно — мы не подменяем запросы, а только
читаем заголовки. Ключевая мысль: мы не сторонний клиент, мы тот же
клиент, что и сам сайт, поэтому никакой регистрации не нужно.

Клиентский `client_id` лежит не в поле `client_id`, а в гидратации главной
страницы: `{"hydratable":"apiClient","data":{"id":"so5r9Dsxv6…"}}`.

Не разведено одно: **Discord RPC `client_id` общий** (`1501214545136586792`).
Это идентификатор приложения в самом Discord, он не принадлежит сборке.
Обе версии, запущенные одновременно, будут драться за presence —
последний записавший победит. Свой client_id можно получить, заведя
приложение на discord.com/developers.

| | было (electron) | стало (tauri) |
|---|---|---|
| инсталлятор | 101 МБ | **3.47 МБ** |
| приложение | 223 МБ | **11.1 МБ** |
| бандл фронтенда | 11 МБ asar (из них 3 МБ babel) | 1.16 МБ js + 6 КБ css |

### про снапшот

`tools/extract-renderer.mjs` читает **не** живой `renderer/index.html`
electron-репозитория, а `tools/snapshot/index.html` — копию на момент
начала миграции. Оригинал продолжает дописываться, и если бы скрипт читал
его напрямую, повторный запуск молча затянул бы в миграцию чужую работу
(в том числе незаконченные эффекты слов в lyrics). Чтобы перегенерировать
из другой версии — путь передаётся явно:

```bash
node tools/extract-renderer.mjs C:/seWer/renderer/index.html
```

Правок в логике ui скрипт делает ровно две, обе про протокол, а не про
поведение: глобалы `React`/`Motion` → импорты, и `audio.src = 'file:///…'`
→ `fileSrc()` (webview не видит file-ресурсы). Список лежит в `PATCHES`
в начале скрипта.

## команды

```bash
npm install
npm run app:dev      # tauri dev  (vite поднимается сам)
npm run app:build    # tauri build → src-tauri/target/release/bundle/nsis/*.exe
npm run build        # только фронтенд (проверка компиляции jsx)
```

`npm run app:*` идёт через `tools/tauri.mjs`: rustup кладёт cargo в
`%USERPROFILE%\.cargo\bin`, а tauri cli ищет его в PATH и без этого падает с
невнятным «program not found». Обёртка подкладывает путь сама.

Проверить только rust-часть, без сборки фронтенда:
`powershell -ExecutionPolicy Bypass -File tools\check-rust.ps1`

- `npm run build` — проходит
- `cargo check` — проходит, без warnings
- `npm run app:build` — проходит
- **ui отрисован и проверен в браузере**: 44 КБ разметки, 19 кнопок,

- **приложение запущено пользователем**: окно, рендер, плавность — ок;
  по его итогам починены csp (не играла музыка) и логин soundcloud
- **проверено вживую, работает**:
  - вход в soundcloud (окно скрывается, сессия живёт, токен сохраняется)
  - редактирование плейлистов: `PUT` уходит из страницы soundcloud,
    DataDome его пропускает, проверка по `GET /playlists/{id}`
  - обложки soundcloud: 1292 файла в кэше, 4 трека из тысячи отдают 404
    на самом CDN (битые данные, не наш баг)
  - discord rpc: подключение, присутствие с картинкой и таймером
  - локальные треки, чип плейлиста с суммарной длительностью
- **не проверено вживую**: загрузка трека с soundcloud (скачивание файла),
  трей, перетаскивание окна, автозапуск

Третий невидимый для компилятора баг — тоже в логине. `eval_with_callback`
отдаёт результат уже сериализованным, то есть объект приходит
**дважды** сериализованным (`"{\"ok\":true,...}"`). Один `from_str` давал
`Value::String`, `v.get("ok")` — `None`, `ok` всегда `false`: токен лежал
в руках, а цикл крутился до таймаута. Плюс на успешном пути не было паузы —
67 тысяч опросов за 8 минут. Оба бага видны только в логе, не в коде.

Четвёртый — уже после починки. На странице входа, **до** авторизации, в
`localStorage` полно строк длиной 20+ символов (csrf, session-ключи).
Регулярка пробника брала первую попавшуюся, и логин принимал
`I7FB0AFFMEE3UF2NA1NJFBSOFO` за токен, а потом ещё и делал `break`, не
дождавшись настоящего. Теперь токен сверяется с формой
`2-332396-1366999722-sKbZ4vNW6wdsB` (две проверки: в пробнике и в Rust —
скрипту с чужой страницы доверять нельзя), а отсутствие `client_id`
больше не прерывает ожидание.

Пятый — «вылет ровно в момент успешного логина». `on_window_event` в
lib.rs стоял глобально, а окон два: главное и окно входа soundcloud.
Закрывая окно входа, `sc_login` вызывал `CloseRequested` → `exit_now()` →
приложение умирало. Теперь обработчик смотрит на `window.label()`.
Это тот же класс бага, что и `ReactDOM is not defined`: компилятор молчит,
работает всё, ломается в момент, когда срабатывает другая ветка.

Из того, что чинилось по итогам живого запуска, два бага были принципиально
невидимы для статических проверок: `ReactDOM is not defined` (ошибка только
в рантайме) и csp, режущий `media-src` (сборка проходит, файлы отдаются,
но браузер блокирует). Общий урок: логин и медиа нельзя подтвердить ни
компилятором, ни запуском — только руками.

Проверка ui в браузере окупилась: она поймала `ReactDOM is not defined` —
порталы шли через глобаль из cdn-скрипта, который в es-модуле не существует.
Без неё сборка выглядела бы рабочей, а окно было бы пустым.

## правки ui, пришедшие из electron-репозитория

`src/app.jsx` не генерируется из живой `renderer/index.html` оригинала, а из
замороженного `tools/snapshot/index.html`. Поэтому правки разметки, сделанные
в electron-версии позже, нужно переносить вручную — и обязательно заносить в
`PATCHES` в `tools/extract-renderer.mjs`. Иначе они молча пропадут при первом
же перегенераторе: снапшот старый, скрипт отработает без ошибок и вернёт
прежнюю разметку. Сейчас в PATCHES лежат четыре правки, из них две — про
протокол, две — про разметку:

- **чип плейлиста в плеере.** Капс «ПЛЕЙЛИСТ» убран — он повторял то, что уже
  сказано названием, и `t('nav_playlists')` в этом месте читался как «это та
  вкладка сверху», потому что ключ общий с вкладкой топбара. Название поднято
  наверх с `title`-тултипом, под ним мета: счётчик треков и суммарная
  длительность в `H:MM:SS` (у `fmt` минуты без разряда часов, поэтому своя
  утилита `fmtHMS`; часы выводятся всегда, даже когда их ноль, иначе колонка
  прыгает по ширине). При 0 длительность прячется: у недогруженных треков sc
  `duration` нет, и `0:00:00` читалось бы как «пустой плейлист». Сумма в
  `useMemo` по `playlistActive`.

Проверено: `node tools/extract-renderer.mjs` даёт байт-в-байт тот же
`app.jsx`, что и правка руками; `vite build` собирается; `fmtHMS` прогнан на
границах (0 / 59 / 3600 / 12:34:56 / 99:59:59 и мусор на входе: `-5`, `NaN`,
`undefined`, строка → `0:00:00`). В живом окне не проверялось — там нужен
открытый плейлист.

## запись в soundcloud api заблокирована DataDome (PUT)

Редактирование плейлистов не работает: `PUT` получает 403 с телом, где
`geo.captcha-delivery.com/captcha/`. Это DataDome, и куками не лечится.

Изолирующий эксперимент, все запросы с валидным токеном и тем же UA, что
шлёт приложение:

| запрос                          | результат          |
| ------------------------------- | ------------------ |
| `DELETE /me/follow/1`           | 404 — дошло до api |
| `POST /me/playlists`            | 404 — дошло до api |
| `PUT /playlists/1` без тела     | **403 captcha**    |
| `PUT /playlists/1` с json-телом | **403 captcha**    |

DataDome режет именно `PUT`, независимо от тела, при этом `GET`, `POST` и
`DELETE` проходят. Свой client_id не поможет: дело в методе и отпечатке, а
не в регистрации. Куками тоже: у reqwest TLS-отпечаток не как у Chrome, а
DataDome смотрит именно на него.

Рабочий путь — тот же приём, что и в логине: писать через живой webview с
настоящей сессией soundcloud. Окно входа после логина не закрывается, а
прячется и живёт до конца сессии; `PUT` уходит через `fetch` внутри
страницы, где куки и отпечаток настоящие. GET остаётся в Rust — он
работает. Реализовано в `sc_write_via_page`; откат на прямой запрос есть на
случай, когда окна ещё нет, чтобы не ломать то, что работало.

Тонкость реализации: `eval` результата промиса не дожидается, поэтому запрос
запускается первым eval'ом, ответ пишется в `window.__sewerWrite` и
забирается вторым eval'ом с опросом. Пробник на «ещё нет» отдаёт строку
`wait`, а не json — её нельзя пропускать через общий разбор, иначе write
сдался бы с нулевым статусом на первой попытке.

**Тело запроса подставляется в js строкой, а не объектом.** `fetch` с
телом-объектом приводит его через `String(obj)` и отправляет
`[object Object]`, а soundcloud отвечает `400 {"errors":["Unable to parse
JSON"]}` — при вроде бы правильном теле. Ответ из страницы теперь
возвращает `sent`, сколько байт тела ушло на самом деле, чтобы это больше
не приходилось вычислять умозрительно.

**Проверка сохранения.** Эндпоинт `GET /playlists/{id}/tracks` у soundcloud
отдаёт 404 (проверено curl'ом на живой учётке), а треки лежат прямо в
`GET /playlists/{id}`. Хуже всего: при ошибке проверка возвращала `true`,
то есть «не смогли проверить» выдавалось за «сохранено» — редактор
закрывался, ничего не изменив. Теперь проверяем `/playlists/{id}` и при
любой ошибке возвращаем `false`.

**Почему эндпоинт `/playlists/{id}/tracks` отдаёт 404.** Раньше здесь стояло
«значит плейлист не принадлежит пользователю, редактированию не подлежит».
Это было неверно, и проверено на живой учётке: `2282654457` — собственный
плейлист пользователя (`user_id` совпадает, 28 треков), а
`GET /playlists/{id}/tracks` всё равно отдаёт 404. Просто этот эндпоинт не
работает, а треки лежат в `GET /playlists/{id}`. Путать «эндпоинт сломан» с
«плейлист чужой» опасно: интерфейс начал бы отказывать в правке законного
плейлиста.

Rust-часть писалась по памяти, без документации под рукой: 30 ошибок
компиляции, все исправлены по исходникам крейтов.

## discord rpc: три ошибки в протоколе, найденные разговором с каналом

Всё выяснено не чтением кода, а прямым разговором с `discord-ipc-0` через
node `net.connect` в обход всей rust-части. Канал на машине открыт, так
что ответ сервера можно получить и увидеть целиком.

Формат кадра: `[op: u32 LE][len: u32 LE][json]`. Три ошибки, все в ported
коде:

1. `write_frame` клал байт `op` внутрь тела перед json. Discord отвечал
   кодом 1003 «Unexpected token '\u0001'» — то есть прямо называл проблему.
2. `reader_loop` брал первые 4 байта и объявлял их длиной: за длину
   принимался сам `op`, настоящее поле `len` не читалось, поток сдвигался
   на 4 байта. Плюс json читался из `buf[1..]`, будто в теле лежит байт
   op, но его там нет.
3. `is_alive()` требовал `pid > 0` из READY. В проверенном ответе поля
   `pid` нет вообще: `{"cmd":"DISPATCH","data":{"v":1,"config":{…},
   "user":{…}},"evt":"READY"}`. Даже с правильным кадром соединение не
   признавалось живым. Присутствие отправляется с `pid: 0`, discord такое
   принимает.

Порядок: HANDSHAKE уходит сразу при подключении, `op = 0`; сервер HELLO
не присылает. Проверенная цепочка: HANDSHAKE → READY → `SET_ACTIVITY` с
ответом, где discord возвращает `application_id` и имя приложения —
`client_id` валиден, менять его не нужно.

**Обложки в присутствии: откуда url.** Рендерер отдаёт в discord только
`https://` и `data:image`, поэтому sc-обложка терялась: после скачивания в
кэш её url становится `http://asset.localhost/…`, и ни под одну проверку не
подходил. В electron это не проявлялось только потому, что кэш обложек там
не работал и url оставался https-ссылкой — то есть баг был и там, просто
замаскированный неработающим кэшем. Теперь asset-ссылка разбирается до пути
на диске, файл читается и загружается в discord тем же путём, что и data-url.

**Формат присутствия: плоские поля discord не понимает.** Найдено не
чтением документации, а перебором вариантов прямо в живом канале с
подтверждением скриншотами. Discord принимает payload, отвечает эхом, ошибок
не даёт — и при этом молча рисует заглушку:

| что отправляли                              | что показал discord        |
| -------------------------------------------- | -------------------------- |
| `large_image_key: <url>`                     | серая заглушка «?»         |
| `assets: { large_image: <url> }`              | **настоящая картинка**     |
| `startTimestamp` / `start_timestamp`, мс      | таймер `0:00`              |
| `timestamps: { start, end }`, мс             | таймер `0:00`              |
| `timestamps: { start, end }`, **секунды**     | **таймер и прогресс-бар**  |

То есть работают вложенные `assets` и `timestamps` (так их и отправляла
библиотека `discord-rpc` в оригинальном electron), а время — в **секундах**
unix, а не в миллисекундах. Эхо discord не годится как проверка: оно
возвращает ровно то, что прислали, включая поля, которые клиент потом
игнорирует. Единственный способ — смотреть на отрисовку.

Общий урок сессии: шесть из семи багов не ловились ни компилятором, ни
сравнением с оригиналом, ни чтением кода. Ловились двумя вещами —
логом в файл и прямым обращением к внешней системе.

## кодировки: две ловушки, обе уже сработали

**1. Windows PowerShell 5.1 на этой машине.** `Get-Content` без `-Encoding`
читает файл в системной ANSI-кодировке (здесь 1251), а `WriteAllText`
записывает обратно в UTF-8. Одно массовое преобразование в `soundcloud.rs`
так испортило всю кириллицу: `логин` → `Р»РѕРіРёРЅ`. Файл продолжал
компилироваться — мусор был валидным UTF-8, — и выглядел как поломка
шрифта в редакторе, а не как поломка данных. Восстановили обратным
преобразованием (строка-мусор → байты cp1251 → исходный UTF-8) с проверкой
на U+FFFD: их ноль значит, что потерь нет и разворот точный.

Правило: **никогда не гонять исходники через `Get-Content`/`Set-Content`
без явного `-Encoding utf8`**, а для правок использовать файловый
инструмент, а не PowerShell. Скрипты-обвязки держать ASCII-only: `.ps1`
без BOM PowerShell тоже читает в ANSI, и не-ASCII литерал в самом скрипте
портится до запуска.

**2. Унаследованная порча в оригинале.** В `renderer/index.html`
electron-версии в одном комментарии «р??зко» вместо «резко» — потеряны оба
байта `ё` (`D1 91`). Через снапшот это попало в `src/app.jsx`. На
функциональность не влияет (это `/* */` в комментарии), но означает, что
`src/app.jsx` нельзя объявлять байт-в-байт валидным UTF-8. В
`library.rs` была та же беда в одном месте — починено.

## что осталось проверить руками

Проверено вживую: логин soundcloud, редактирование плейлистов, обложки
soundcloud, discord rpc с картинкой и таймером, локальные треки, чип
плейлиста. Не проверено:

1. **Загрузка трека с soundcloud** — скачивание файла с прогрессом и
   проставлением id3-тегов. Код написан и компилируется, но живьём
   скачиванием не гоняли.
2. **Трей, minimize-to-tray, перетаскивание окна за тайтлбар, медиаклавиши.**
3. **HLS.** В csp добавлен `worker-src blob:` — hls.js поднимает воркер с
   blob-uri, без этого стримы не играют. Проверялось на тех треках, что
   играют; отдельного теста только на hls-треке не было.
4. **Автозапуск** (ключ реестра `seWer Tauri`) — настраивается, но
   перезагрузку пользователя не проверяли.

Два места, где причина отказа заранее известна, чтобы не искать зря:

- **Запись в api.** `PUT` из reqwest получает 403 с капчей DataDome —
  см. раздел выше. Если что-то перестало сохраняться, сначала смотреть
  `[sc-write]` в логе: там видно, дошло ли тело (`отправлено N байт тела`).
- **Обложки.** 4 трека из тысячи отдают 404 на самом CDN soundcloud, это
  битые данные провайдера, а не миграция. На них `coverUrl` остаётся
  мёртвым и рисуется битая картинка вместо заглушки; чинить нечего.

## отличия поведения, о которых надо знать

- **Данные не теряются.** `%APPDATA%\sewer` зафиксирован руками: tauri
  по умолчанию пишет в `%APPDATA%\com.sewer.app`, и переезд молча обнулил
  бы настройки, кэш лайков и обложек. Сессия webview при этом сохраняется
  в своём каталоге и переживает перезапуск: проверено — повторный запуск
  находит токен за две секунды без нового входа. Именно поэтому окно входа
  после логина прячется, а не закрывается: его куки стали транспортом для
  `PUT` (см. раздел про DataDome).
- **Скорость сбора.** electron гонял 16 воркеров на файлы, здесь rayon.
  Тот же предел: треки короче 30с выкидываются.
- **Прогресс скачивания** шлётся пачками по 128кб, а не на каждый чанк:
  event на 64кб — это ipc-спам ради полосы, которую никто не заметит.
- **Теги после скачивания** пишутся в уже переименованный файл: lofty
  определяет формат по расширению, `.tmp` для него неизвестен. Поведение
  при ошибке то же — файл остаётся, прилетает `warn: tags_failed`.

## ограничения сборки

- Только windows: `discord.rs` использует `std::os::windows::net`
  (именованные каналы discord) и NSIS-инсталлятор.
- Нужен webview2 (на win10/11 ставится вместе с другими приложениями;
  при отсутствии tauri предлагает bootstrap-режим).
- Rust собирается только с MSVC toolchain и windows sdk: на машине без
  них `cargo build` не запустится.
